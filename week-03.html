2026-10-25 / 14:00–17:00 KST

Third regular meetup: voice tarot and team development

Venue
Hyundai Motor and Kia headquarters, Yangjae

The team changed the MIND DETOXING concept to voice tarot. The first version will use a mobile website with an immediate voice connection. The product name and voice provider remain open.

Decisions from the meeting

  • Build a two-way tarot conversation. The user explains a question, selects a card, hears an interpretation, and asks follow-up questions.
  • Start with a mobile website. The user starts a voice session inside the website. A telephone number is not necessary.
  • Use a cute, playful visual direction. The team still needs to choose the character and detailed design.
  • Consider scheduled calls and payments after the immediate connection works.
  • Let members work on features across disciplines. Product, frontend, and backend coordinators will help resolve differences.
  • The goal is a working product and a successful December 16 demo. Sona remains an optional tool.

What the discussion clarified

  • The same product description led to different expectations. The specification must show the screens and conversation sequence together.
  • The reader must speak the interpretation. A spoken greeting followed by a text-only result does not meet the intended experience.
  • Do tests of Korean pronunciation, response delay, interruption, and character tone with real conversations.
  • Compare OpenAI and ElevenLabs before the provider decision. Their APIs have different interfaces.

Progress and remaining work

  • The team selected the product direction. A working product and live voice test results are not yet available.
  • The next checkpoint is one complete mobile flow: start, conversation, card selection, spoken interpretation, and end.
  • The proposed schedule has a November 30 demo milestone. Presentation practice follows. The submission dates need confirmation from the organizer.
  • The leader will prepare the first specification, API comparison, and shared development setup. Members will review the specification and select tasks.
  • Make a decision about the intended users, name, character, provider, cost limits, hosting, and task owners.

GitHub and Codex workflow proposal

  • These are proposed rules for development after v1.0. The meeting did not approve these detailed procedures.
  • Create an Issue before each task. Record the purpose, scope, acceptance criteria, owner, and reviewer.
  • Create one branch per task from the latest main branch. Do not commit directly to main.
  • Ask Codex to read AGENTS.md and the Issue. Examine its plan before implementation.
  • Open a small draft pull request early. Include the Issue, reason for the change, test results, and screenshots when applicable.
  • Ask another member to examine the change and user flow. Use Codex code review as additional help.
  • The leader is the first integration maintainer. This person examines the peer review and CI results before a squash merge.
  • Another member must examine the leader’s changes. Select a second integration maintainer for absences.
  • Resolve conflicts with the other task owner. Ask the relevant coordinator for help with product or interface decisions.
  • Use CI for type checks, lint checks, tests, and the build. Use test adapters without production secrets or paid API calls.
  • Deploy main to a test environment after checks pass. Check the main user flow before deployment to the demo environment.
  • Use GitHub Projects: Backlog, Ready, In progress, In review, and Done. Mark work Done after deployment verification.
  • Keep keys, raw audio, and personal conversations out of the repository. Record contributions through results, reviews, tests, and documentation.
  • Ask each member about preferred work, available time, blockers, and support needs. Record important decisions in the repository.
